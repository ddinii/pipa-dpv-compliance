# LLM Fact 추출 실험 결과 (PoC1 · PoC2)

작성: C (LLM 실험 담당) · 2026-09-30 · 브랜치 `feat/fact-pipeline-and-eval-harness`
기준 커밋: `7ea4160` · 모델: `claude-sonnet-5`

> 이 문서는 jejal 핸드오프 ⑤ "LLM 실험/평가 및 결과 정리"의 산출물입니다.
> 세부 기록과 실행 방법은 [evals/README.md](README.md)에 있습니다.

## 1. 요약

- 최종 코드에서 **모든 평가 세트의 Rule 판정이 정답과 100% 일치**했습니다
  (PoC1 dev 42/42, PoC1 held-out 24/24, PoC2 dev 28/28, PoC2 held-out 12/12).
- **위험 오판(GREEN·N/A)은 0건**입니다. 최종 코드의 모든 실행과, 직전 코드의 3회 반복에서
  모두 같았습니다.
- Fact 단위 F1은 0.994~1.000입니다.
- 첫 전체 실험에서는 PoC1 위험 오판이 3건 나왔습니다. 실제 API로 돌려야만 드러나는 결함
  10건을 찾아 고친 결과입니다 (5장).
- 명시적 부재("제공하지 않습니다", 통지문 없음)가 N/A로 이어지는 경로를 만들어, PoC마다
  GREEN/AMBER/RED/N/A 네 상태를 모두 재현합니다 (TST-003).

- LLM은 **Fact만 추출**합니다. 판정은 결정적 Rule Engine이 합니다 (CLAUDE.md §5).
- GREEN은 법적 준수 인증이 아니고, RED는 위반 확정이 아닙니다.
- 모든 평가 문서는 **합성 데이터**입니다. 실제 처리방침·사고 자료는 쓰지 않았습니다.

## 2. 무엇을 쟀는가

### 파이프라인

```
문서 ──LLM──> Fact(35개 중) ──검증──> RDF ──> P0 Rule Engine ──> GREEN/AMBER/RED/N/A
                 │                                              │
            Fact 단위 채점                                 Rule 단위 채점
```

PoC1(처리방침)은 2-pass입니다. Pass 1이 처리행위를 식별하고, Pass 2가 처리행위마다
Fact를 추출합니다. 처리행위 경계가 곧 호출 경계라 서로 다른 처리행위의 값이 섞이지
않습니다. PoC2(침해사고)는 사고 기록과 통지문을 **별도 호출**로 처리해 둘이 섞이지 않습니다.

근거 위치(offset)는 LLM에게 시키지 않습니다. 원문 인용을 받아 코드가 위치를 찾고,
원문에 없는 인용은 Fact를 버립니다 (NFR-07).

### 평가 세트

| | dev (프롬프트를 고칠 때 봄) | held-out (프롬프트를 고칠 때 보지 않음) |
|---|---|---|
| PoC1 | SC-P01 기준 + 변형 6 = **7건** | **4건** (목록형, 서술형, 부재 명시, 부분 부정 함정) |
| PoC2 | SC-P02 기준 + 변형 6 = **7건** | **3건** (날짜 표기 혼합, 경위 누락, 통지문 없음) |

- dev는 PoC마다 시나리오가 하나이고 프롬프트를 고칠 때 이미 봤습니다. 그래서 일반화는
  **held-out으로만** 말합니다.
- 두 세트 모두 PoC마다 GREEN/AMBER/RED/**N/A** 대표 사례를 포함합니다 (TST-003).
- 기대 판정은 Rule 조건을 읽고 손으로 적었고, 정답 Fact로 엔진을 돌려 그 판정이
  재현되는지 테스트가 확인합니다.

### 지표

| 지표 | 뜻 |
|---|---|
| **위험 오판(GREEN)** | 정답이 GREEN이 아닌데 GREEN으로 판정. 문제를 준수로 보이게 한다 |
| **위험 오판(N/A)** | 정답이 RED/AMBER인데 N/A로 판정. 잘못된 "하지 않음" 선언이 결함을 판정에서 뺀다 |
| Rule 일치 | 판정이 정답과 같은 비율 |
| Fact F1 | (Fact 종류, 처리행위, value_state)가 맞은 비율 |
| 환각률 | 원문에 없는 값을 실은 Fact 비율 |
| 처리행위 혼합률 | 다른 처리행위의 값을 가져온 Fact 비율 |

**헤드라인은 위험 오판입니다.** Fact 하나를 놓쳐도 판정이 안 바뀌면 실무 영향이 없지만,
판정이 GREEN이나 N/A로 뒤집히면 검토자가 문제를 놓칩니다.

## 3. 최종 결과

### 최종 코드 (`7ea4160`)

| | 케이스 | 실행 | Rule 일치 | 위험 오판 (GREEN / N/A) | Fact F1 | 환각률 | 처리행위 혼합 |
|---|---|---|---|---|---|---|---|
| PoC1 dev | 7 | 1회 | 42/42 | 0 / 0 | 1.000 | 0.000 | 0.000 |
| PoC1 held-out | 4 | 2회 | 24/24, 24/24 | 0 / 0 | 0.994, 1.000 | 0.012, 0.047 | 0.000 |
| PoC2 dev | 7 | 1회 | 28/28 | 0 / 0 | 1.000 | 0.000 | 0.000 |
| PoC2 held-out | 3 | 2회 | 12/12, 12/12 | 0 / 0 | 1.000, 1.000 | 0.000 | 0.000 |

**환각률 0.047에 대하여**: 전부 서술형 문서(held-out h2) 하나에서 나왔고, 값을 지어낸 것이
아니라 원문을 조금 바꿔 적은 것입니다 ("…관리하기 위하여" → "…관리하기 위함",
"수신 동의를 철회할 때" → "수신 동의 철회 시"). 근거 인용은 원문 그대로이고 판정에는
영향이 없습니다. 채점기가 값이 원문에 글자 그대로 있는지를 보기 때문에 환각으로 셉니다.
held-out에서 나온 것이라 프롬프트에 반영하지 않았습니다.

**F1 0.994**: 제공 처리행위 하나의 `absent` Fact를 모델이 빠뜨렸습니다. 판정에는 영향이 없습니다.

### 반복 안정성 (직전 코드, 3회)

LLM 출력은 실행마다 조금씩 다릅니다. 최종 코드 직전 버전으로 모든 세트를 3회씩 돌렸습니다.

| | Rule 일치 (3회) | 위험 오판 | Fact F1 (3회) |
|---|---|---|---|
| PoC1 dev | 42/42 ×3 | 0 | 0.993 / 0.996 / 0.996 ¹ |
| PoC1 held-out | 18/24 ², 24/24, 24/24 | 0 | 0.965 / 1.000 / 1.000 |
| PoC2 dev | 28/28 ×3 | 0 | 1.000 ×3 |
| PoC2 held-out | 12/12 ×3 | 0 | 1.000 ×3 |

¹ 정답지 v1·v5 정정 후 저장된 예측을 다시 채점한 값입니다 (API 재호출 없음).
² 5장 10번 결함(`fact_id` 번호 붙임)으로 문서 하나의 판정이 통째로 빠진 회차입니다.
  이 결과로 결함을 찾아 고쳤고, 최종 코드에서는 재현되지 않습니다.

직전 코드와 최종 코드의 차이는 세 가지입니다.

- `fact_id`를 enum으로 제한 (PoC1·PoC2)
- 처리행위별 호출을 동시에 보냄. 결과는 순차 실행과 같음을 테스트로 고정 (PoC1)
- 보유기간과 종료조건을 "끝이 어떻게 정해지는지"로 구분 (PoC1, 6장)

### 판정 분포 — 네 상태가 모두 나옵니다

| | GREEN | AMBER | RED | N/A |
|---|---|---|---|---|
| PoC1 | 기준 문서 등 | P1-R02 보유정보 불명확, 모호한 파기방법 | 목적 누락, 수탁자명 누락 | 제3자 제공·위탁 안 함 명시 |
| PoC2 | 기준 문서 | 대응조치 일부만 | 통지 항목 누락, 경위 누락 | 통지문 없음 |

held-out에는 잘못된 N/A를 잡는 함정(h4)을 넣었습니다. "원칙적으로 제공하지 않습니다. 다만
다음의 경우 제공합니다" 뒤에 목적이 빠진 제공이 이어집니다. 모델이 이를 부재로 보면 RED가
N/A로 바뀌어 결함이 사라집니다. **모든 실행에서 한 번도 부재로 보지 않았습니다.**

## 4. 실제 서버 경로

평가 러너가 아니라 FastAPI 서버(`PIPA_EXTRACTOR=llm`)로 요청을 보내 확인했습니다.

| 요청 | 결과 |
|---|---|
| PoC1 (제3자 제공 안 함 명시) | 정답과 일치, P1-R03 N/A |
| PoC2 기준 | 정답과 일치, 날짜 `2026-09-05T14:30:00+09:00` |
| PoC2 (통지문 없음) | 정답과 일치, P2-R02·R03 N/A |

- 기능명세서 §9.1 응답 봉투, §8 `source_document_id` 등 필수 필드가 모두 있었습니다.
- 서버 로그에 API 키나 원문이 남지 않았습니다.
- PoC1 응답 시간: 순차 호출 88초 → 처리행위별 호출 동시 실행 후 약 41초.
  캐시 적중률은 80%로 같았습니다.
- 화면은 브라우저로 확인하지 않았습니다.

## 6. 팀 결정 사항

| 결정 | 내용 |
|---|---|
| 날짜 | 저장은 KST ISO 8601(`2026-09-05T14:30:00+09:00`), 화면은 `2026-09-05 14:30 (KST)` |
| "관계 법령에서 정한 기간" | 법령을 연동해 채우지 않고 **알 수 없음(unknown)**. 어느 법령인지 추정하는 것은 법적 판단이다 |
| 보유기간 vs 종료조건 | "기간"이라는 단어가 아니라 **끝이 어떻게 정해지는지**로 가른다. 시간 길이 → F1-03, 사건 → F1-04, 둘 다 모름 → F1-03 unknown |
| 기재가 없는 항목 | Fact를 빼지 않고 `absent`로 둔다 (Fact Dictionary 8장) |
| 명시적 부재 | Fact가 아니라 activity presence metadata(`confirmed_false`). 35개 Fact는 그대로 |
| 기본 모델 | `claude-sonnet-5` |

Fact Dictionary 본문에 반영할지는 Fact 담당자 결정 사항입니다 (기능명세서 §14-3).

## 7. 한계

- **합성 데이터**입니다. 실제 처리방침의 문체와 분량은 더 다양합니다.
- held-out이 PoC1 4건, PoC2 3건으로 작습니다. 결과는 "이 문서들에서 이렇게 동작한다"까지만 말합니다.
- held-out 정답 1건을 모델 결과를 본 뒤 고쳤습니다 (PoC1 h2 수탁자명, absent → unknown).
  dev 규약에 비추어 정답지가 틀렸다고 판단했지만, 그 한 건은 독립적인 측정이 아닙니다.
- held-out은 프롬프트 수정 뒤 **회귀 확인용으로 다시 돌렸지만** 그 결과로 프롬프트를 고치지는 않았습니다.
- **Opus 5는 수정 후 다시 돌리지 않았습니다.** 기본 모델 선택은 공정한 비교에 근거하지 않습니다.
- LLM 출력은 실행마다 조금씩 다릅니다. 최종 코드는 세트마다 1~2회 실행했고, 흔들림의 폭은
  직전 코드의 3회 반복으로 확인했습니다 (3장).
- 시행령 기한·통지 의무 판정은 P0 범위 밖이라 다루지 않았습니다.

## 9. 재현

```powershell
$env:ANTHROPIC_API_KEY = "..."   # 본인 키. 소스나 파일에 넣지 않는다
python evals\run_extraction.py --poc poc1 --split dev     --model claude-sonnet-5
python evals\run_extraction.py --poc poc1 --split heldout --model claude-sonnet-5
python evals\run_extraction.py --poc poc2 --split dev     --model claude-sonnet-5
python evals\run_extraction.py --poc poc2 --split heldout --model claude-sonnet-5
python evals\compare_runs.py evals\poc1\predictions\runs
```

러너는 위험 오판(GREEN 또는 N/A)이 하나라도 있으면 종료 코드 1로 끝납니다.
